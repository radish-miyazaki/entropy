## TL;DR

- テストを後から書くと、実装中にフィードバックが得られず、エッジケースのバグも見つけにくい。
- [[test-driven-development|TDD]] の本質はテストファーストではなく「迅速な反復」であり、それがコーディング体験そのものを変える。

## 内容

### テストを後から書くことの欠点

この章のテーマは、[[jest|Jest]] による[[test-driven-development|テスト駆動開発]]である。「テストを後から書く」アプローチには、次の 3 つの欠点がある。

1. 機能を実装している間にフィードバックを受け取れない。
2. 実装後に書いたテストは、想定どおりに動くことを確かめるだけになりやすい。そのため、エッジケースで起きるバグを見つけられない。
3. 既存のコードの構造を見直さずに機能を足そうとする。他の機能を壊すかもしれないという不安から、[[refactoring|リファクタリング]]を避けがちになる。

これらの欠点は、TDD の重要な要素である「テストを先に書く」（テストファースト）ことで避けられる。

### TDD の本質は迅速な反復

ただし、テストファーストは TDD で重要ではあるが、本質ではない。TDD の本質は「迅速な反復」であり、次の流れを繰り返す。

1. 小さなテストを 1 つ書く。
2. そのテストが失敗することを確かめる。
3. テストをパスするだけの実装を書く。
4. テストがパスすることを確かめる。
5. Git で進捗を保存する。

TDD はコードカバレッジを上げるだけでなく、コーディング体験を変える。テストが先にあれば、何がうまくいき何がうまくいかないかというフィードバックをすぐに確認できる。そのおかげで、さまざまなアプローチを試せるし、クリーンなコードにするためのリファクタリングもできる。この「実験」が学びにつながり、より良いコードを生む。
