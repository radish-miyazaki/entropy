## TL;DR

- タスクは担当者ごとではなく、プロジェクトの構造で分ける。フロントエンドとバックエンドをまたいで独立して終えられるまとまりを Scope と呼ぶ。
- Scope は計画で決めるものではなく、作業しながら見つける。1 週目の終わりから 2 週目の初めに見えてくることが多い。
- Scope の種類（Layer cake、Iceberg）を見分け、どこにも入らないタスク（Chowder）や nice-to-have（~ を付ける）を扱う。

## 内容

前の章の、一部分をつないで作るやり方はプロジェクト全体で使うもっと一般的な手法の一部である。

### 人ではなく構造で分ける

デザイナ用、プログラマ用のように役割でリストを分けると、全体像が見えなくなる。一部分をつなぐやり方をすると、それがよく分かる。募金イベントの準備なら、ボランティア 3 人ごとではなく、料理、会場の設営、照明と音響でリストを分ける。

プロダクトの仕事では、分け方が前もって決まっていない。どのプロジェクトも未開の土地である。フロントエンドとバックエンドの作業をつなぐまとまりを Scope と呼び、プロジェクト全体を、それぞれ独立して終えられる Scope に分ける。

### Scope の地図

Scope の地図は頭の中に描く図である。チームは形を決めた大枠から始め、細かいタスクで埋めていく。実際の作業で構造が見えてきたら、それをいくつかの領域に分ける。

Scope は問題の意味のある一部分で、数日以内に独立して終えられる。実際には、Scope ごとにその名前の To-Do リストを作り、タスクを入れる。例として、フォームの入力欄、場所のプリセット、予定の移行、一覧での表示、といった名前が挙がっている。

### プロジェクトの言葉

Scope は、チームが大きな単位で話すための言葉になる。クライアント招待の例なら、「Bucket Access が終わったら Invite Clients を実装できる」と話せる。進み具合を報告するときも、残っている個々のタスクの言い訳をせず、完成したソフトウェアの部分を指し示せる。進み具合の見せ方であるヒルチャートは次の章で扱う。

### 事例: メッセージの下書き

デザイナとプログラマが、新しいアプリで下書き機能を作った。最初は Scope に分けていないタスクが 10 個あった。目に見えるものを作るため、デザインのタスク 1 つで終えられる「新規作成」の Scope をつないだ。残りのタスクは「探す」「ゴミ箱」「保存・編集」に分けた。「保存・編集」は後で「送信」「保存」「返信」に分けた。最後に地図の Scope がすべて終わり、プロジェクトが完了した。チームはプロジェクト全体を高い位置から見渡せたと感じた。

### Scope を見つける

Scope の地図は計画ではない。実際に土地を歩いて見つけるもので、本当の依存関係を映す。正確な Scope が見えるのは、たいてい 1 週目の終わりか 2 週目の初めである。下書きの例のように、入れ替えたり名前を変えたりするのは普通のことである。

### Scope が正しいかどうかの見分け方

本は体の解剖図にたとえている。Scope が正しいときの兆しは 3 つある。

- 隠れた心配なしにプロジェクト全体が見える
- 会話がよどみなく進む
- 新しいタスクがどこに入るかがすぐ分かる

引き直したほうがよい兆しも 3 つある。

- タスクどうしに関係がなく、終わったかどうかを判断しにくい
- 「フロントエンド」や「バグ」のように名前がありきたりで、何でも入る寄せ集めや、がらくた入れの引き出しになっている
- 大きすぎてすぐには終わらない

### Layer cake

情報システムのアプリの多くは、UI の下に薄いバックエンドが均等に広がる Layer cake である。UI の面積で進み具合を判断できるので、デザインとプログラミングのタスクを同じ Scope に入れてよい。

### Iceberg

UI に比べてバックエンドがずっと複雑な仕事もある。e.g. 送信すると複雑なビジネスロジックが動くフォーム。これを Iceberg と呼ぶ。UI を切り離し、バックエンドの複雑な部分を Scope に分け、その複雑さが本当に必要で減らせないものかを問う。逆に UI が複雑な仕事にも同じ問いをする。e.g. 数日にまたがる予定をカレンダーのマス目で折り返して表示する。

### Chowder

どの Scope にも入らない細かいタスクは「Chowder」のリストに入れる。このリストはよく見ておく。項目が 3〜5 個を超えたら何かがおかしく、新しい Scope を引くべきかもしれない。

### nice-to-have には ~ を付ける

途中で見つけた改善点は Scope のタスクとして先頭に「~」を付けて書く。こうすると must-have と nice-to-have を見分けられる。「~」はスコープを削るときの主な道具で、[[Shape Up： Stop Running in Circles and Ship Work that Matters 第14章 Decide When to Stop|第 14 章]]で扱う。
